### ② 점수 비교군 수정 — 가장 시급

**무엇이 문제인가**
적격 308곳의 점수가 **25.7점(216곳)과 93.7점(92곳) 두 값뿐**입니다. 순위를 매길 수 없습니다.
점수 중앙값 25.7 (정상 47~53), 90점 이상 29.9% (정상 0~2%).

**왜 그런가 (원인까지 확인했습니다)**
점수는 비슷한 단지끼리 비교한 편차(robust z-score)로 냅니다.
`common/peer_group.py`의 `calculate_robust_z_score()`는 편차(MAD)가 0이면 `0.0`을 반환합니다(22~23행).

비교군을 만드는 `select_peer_group()`에 넘기는 대상이 **게이트에서 제외된 단지까지 포함한 전체**입니다.
제외된 단지는 거래가 없어 통계값이 전부 같은 폴백값이고, 그 수가 압도적입니다.

실측: 서초구 25평형 비교군 103곳 중 **66곳(64%)이 완전히 동일한 값** → MAD = 0 → 모든 편차가 0.
같은 비교군을 적격 28곳으로 좁히면 MAD 0.019로 정상 분포가 나옵니다.

블록 점수를 보면 Value·Flow·Location 세 블록이 308곳 전부 0.0이고,
Quality 블록만 0.0 또는 0.2로 갈립니다. 그 차이가 25.7 / 93.7을 만듭니다.

**어떻게 고치는가**
1. 비교군을 게이트 통과 단지로만 구성합니다. `pc/scoring/scorer_v3.py`와 `scorer_v2.py`가
   `select_peer_group(it, all_items, ...)`에 넘기는 `all_items`가 문제의 지점입니다.
   다만 게이트 판정이 비교군 커버리지에 의존하므로 **순환이 생기지 않는지 확인이 필요합니다.**
   (게이트 → 비교군 → 점수 순서를 다시 설계해야 할 수 있습니다.)
2. `min_peer_n`을 적격 단지 기준으로 다시 잡아야 합니다.
   `config/scoring_v3.yaml`의 `universe.min_peer_n`이 **20**입니다.
   (코드의 기본값 10은 설정이 없을 때만 쓰입니다 — `scorer_v3.py`)
   비교군을 적격 단지로만 좁히면 20을 못 채우는 조합이 생깁니다. 실측으로
   서초구 25평형은 103곳 → 28곳이 됩니다. 임계값 조정이 함께 필요합니다.

**설계자 질문에 대한 답 — "V10/V11이 왜 이걸 못 잡았나"**
**구현되어 있지 않습니다.** 코드 전체에 `V7`~`V11` 참조가 0건입니다.

| 게이트 | 설계서 | 코드 |
| :-- | :-- | :-- |
| G0~G6 | §11.5 | 구현됨 |
| V1, V2, V3, V4, V6 | §11.5 | 구현됨 |
| V5 | §11.5 | **없음** |
| V7 (단지에 없는 평형), V9 (거래/세대수 비율) | §11.5.1 | **없음** |
| **V10 (4블록 전부 상위 10% → run 실패)** | §11.5.2 | **없음** |
| **V11 (점수 중앙값 50±3 밖 → run 실패)** | §11.5.2 | **없음** |

V10과 V11은 설계서에 **정확히 이 상황을 잡으라고 적혀 있습니다.**
오늘 자가검증에서 나온 두 이상 징후(4블록 상위 10% 92건 / 중앙값 25.7)가 각각 V10·V11에 해당합니다.
