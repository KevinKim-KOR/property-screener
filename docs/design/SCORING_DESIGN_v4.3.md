## 1. 개요 및 배경
v4.3에서는 단순히 "얼마나 빠졌나(가격 하락률)"만 보여주던 대시보드 구조에서 탈피하여, **하락의 질(좋은 하락 vs 나쁜 하락)**을 판별할 수 있는 **입지·임차수요 지표 5종**을 대폭 도입했습니다. 또한 지표 확장에 따라 컬럼이 17~18개로 늘어남에 따라, 사용자 관점에서 필수 정보에 집중할 수 있도록 **UI 컬럼 고정 및 프리셋 시스템**을 개편했습니다.

## 2. v4.3 핵심 개편 항목

### ① UI 컬럼 고정, 평형 표기 개편 및 그룹 프리셋
* **고정 컬럼 (`지역 | 단지명 | 평형`)**:
  * 브라우저 가로 스크롤 시에도 왼쪽에 고정되도록 CSS/JS 구조를 개편했습니다.
  * 고정 컬럼 폭 최적화: `지역(100px) | 단지명(220px, 말줄임 처리) | 평형(130px)`
* **평형 표기 개편**:
  * 기존 `34평형 · 전용 84㎡`에서 **`34평 / 84㎡`**로 직관적이고 간결하게 개선했습니다.
* **그룹 프리셋 버튼 (4개)**:
  * `가격 (기본)`: 최근 거래가 · 전고점 · 전고점 시점 · 하락률 · 초과하락 · 전세가율
  * `흐름`: M3 · M6 · M12 · 거래 건수 · 거래량비
  * `단지`: 연식 · 브랜드 · 역세권 · 학원가 · 학교거리
  * `전체`: 모든 선택 가능 컬럼 표시
  * 개별 컬럼 체크박스 지원 및 브라우저 `localStorage('screener_visible_cols')`에 선택 상태 유지.

### ② 전세가율 (`jeonse_ratio`) 공식화 및 파서 견고성 강화
* **공식**:  
  $$\text{전세가율} = \frac{\text{최근 6개월 전세 보증금 중위 (만원)}}{\text{최근 매매 실거래가 (만원)}} \times 100$$
* **정제 조건**:
  * **순수 전세 계약만 산출**: 월세금이 0원인 계약만 포함(반전세 및 월세 거래 제외).
  * **매칭 기준**: 동일 단지 · 전용면적 5㎡ 버킷 매칭. 최소 2건 이상 실거래 존재 시 산출하며, 미달 시 빈칸 처리.
* **CSV 적재 로직 개선 (`oci/crawler/molit_schema.py`)**:
  * 국토부 전월세 CSV의 실제 헤더인 **`월세금(만원)`**을 정확히 파싱하도록 매핑 수정.
  * 필수 컬럼 누락 시 조용히 0으로 채우지 않고 예외(`KeyError`)를 발생시켜 데이터 누락 및 오염을 근본 차단.

### ③ 단지 좌표 (`lat`, `lng`) 카카오 로컬 API 지오코딩
* **실행 모듈**: `pc/features/geocode_complexes.py`
* **방식**:
  1. `시군구명 + 본번-부번` 지번 주소로 1차 카카오 로컬 API(`dapi.kakao.com/v2/local/search/address.json`) 변환 시도.
  2. 실패 시 `도로명 주소`로 2차 시도.
  3. 실패 시 목록으로 출력 및 유지 (임의 값 기입 금지).
* **결과**: 유효 단지 1,449곳 중 1,444곳 좌표 확보 완료 (5곳은 재건축에 따른 지번 소멸/변경 단지로 정상 확인).

### ④ 역세권 거리 (`subway_str`)
* **실행 모듈**: `pc/features/update_subway_dist.py`
* **방식**: 카카오 로컬 API 카테고리 검색(`SW8` - 지하철역)으로 각 단지 기준 최근접 지하철역과 직선거리(m) 조회.
* **표기 형식**: `강남역 320m`, `사당역 47m` (1.5km 초과 시 빈칸 표시).
* **결과**: 1,444곳 중 1,431곳(99.1%) 역세권 정보 반영 완료.

### ⑤ 학원가 밀도 (`academies_str`)
* **실행 모듈**: `pc/features/update_academies_count.py`
* **방식**:
  * 카카오 로컬 API 카테고리 검색(`AC5` - 학원)으로 단지 반경 1km 내 학원 수 조회.
  * **페이징 상한(45건) 극복**: 단지 주변 학원이 수백~수천 개에 달하는 대치동 특성을 반영하여, 목록 개수가 아닌 API 응답의 **`res.meta.total_count`** 값을 사용하여 정확한 총합 기록.
* **표기 형식**: `학원 87곳`, `학원 1692곳` (단지 프리셋 표시).
* **결과**: 1,444곳(100%) 반영 완료. 대치동 핵심 단지(1,639~1,692곳) 최상단 및 외곽 단지 하위권 분포 검증 완료.

### ⑥ 초·중학교 거리 (`schools_str`)
* **실행 모듈**: `pc/features/update_schools_dist.py`
* **방식**:
  * 카카오 로컬 API 카테고리 검색(`SC4` - 학교, 반경 2km 이내, 거리순 정렬, 최대 3페이지 조회).
  * **정밀 필터링 적용**: `SC4`에 섞여 들어오는 고등학교·대학교·병설유치원·어린이집·버스정류장 등을 모두 배제하고, 이름이 `~초등학교`, `~중학교`(`~여자중학교` 등 포함)로 확인되는 학교의 최근접 직선거리를 각각 추출.
* **표기 형식**: `초 180m / 중 420m` (2km 초과 항목 빈칸 처리).
* **결과**: 1,444곳(100%) 정보 산출 완료. 300m 이내 초근접("초품아") 단지 380곳(26.3%) 확인.

### D15 — 이 저장소에서 반복 발생한 사례

다섯 번 나왔고 전부 결측 처리로 정정됐다.

| 값 | 위치 | 증상 |
| :-- | :-- | :-- |
| 세대수 `300` | `build_complex_master.py` | 전 단지가 같은 값이라 규모 비교가 불가능. 이상 징후 검사 ①③을 판정조차 못 함 |
| 역세권 `500m` | `build_complex_master.py` | 입지 항목이 점수에 아무 영향을 주지 못함 |
| `excess_drop_rate` `0.05` | `build_stats.py` | 지역 통계가 없는데 근거 없는 초과하락률이 DB 에 남음 |
| 양도세 `0` | `capital_gains` | 계산 실패를 0 으로 두면 순현금이 부풀려짐 |
| `area_type` → `"34평"` | `ui_translator` | 알 수 없는 평형이 실제 값처럼 표시됨 |

공통점은 셋이다.

1. **화면에는 정상으로 보인다.** 빈칸이 아니라 그럴듯한 숫자가 뜨므로 아무도 이상하다고 느끼지 않는다.
2. **오래 남는다.** 위 다섯 건은 모두 도입 시점이 아니라 한참 뒤에 다른 작업을 하다가 발견됐다.
3. **하류에서 더 커진다.** 세대수 상수는 이상 징후 검사 두 항목을 무력화했고, 기간 창 상수는 `가격 기준` 라벨까지 틀리게 만들었다.

### 새 코드를 쓸 때

기본값을 두고 싶어지면 **그 값이 없을 때 화면에 무엇이 보여야 하는지를 먼저 정한다.**

- 숨긴다 → `None` 반환, 화면에서 그 줄 제외 (C13)
- 빈칸으로 둔다 → 빈 문자열 반환, 원인을 로그에 남긴다
- 계산을 멈춘다 → 예외를 던진다. 값이 없으면 결과 전체가 무의미한 경우

### D16 — 직접 알 수 있는 값을 간접 지표로 대신하지 않는다

실거래 기준일은 DB 의 `MAX(deal_date)` 로 알 수 있는데
폴더 이름과 마커 파일로 추론하고 있었다.
간접 지표는 생성 조건이 조금만 바뀌어도 어긋난다.

**사례: 배너 기준일이 마커 미생성으로 11일간 멈춤 (2026-09-07)**

배너는 `data/raw/molit/` 아래 날짜 폴더 중 가장 늦은 것을 기준일로 썼다.
폴더는 CSV 가 있거나 `_api_refresh.txt` 마커가 있어야 인정됐다.

마커는 원래 갱신 때마다 무조건 생성됐고, 그래서 API 를 돌리지 않아도
배너가 "오늘 기준"이라고 표시하는 문제가 있었다. 이를 고치면서
**신규분이 있을 때만** 마커를 만들도록 조건을 걸었다.

```python
if (trade_new + rent_new) > 0:
    마커 생성
```

이후 국토부 API 가 4,710건을 돌려줬지만 전부 이미 적재된 건이라
`trade_new + rent_new == 0` 이 됐다. 마커가 생기지 않았고, 배너는
DB 에 9월 3일자 거래가 들어 있는데도 8월 27일에 멈춰 있었다.

**"신규 0건"과 "갱신 안 함"을 같은 것으로 취급한 것이 직접 원인이다.**
그러나 더 근본적인 문제는 자료의 날짜를 파일시스템 상태로 추론한 구조 자체다.
조건을 어느 쪽으로 고쳐도 — 무조건 생성하면 없는 갱신을 있다고 하고,
조건부로 생성하면 있는 갱신을 없다고 한다 — 간접 지표인 한 계속 어긋난다.

**조치:** 기준일을 `MAX(deal_date)`(매매·전월세 중 늦은 쪽)로 직접 읽는다.
마커 생성 로직과 폴더 스캔 코드를 제거했다.
`data/raw/molit/` 의 CSV 원본은 Point-In-Time 복원용으로 계속 보관한다 —
없앤 것은 **배너가 그것을 참조하던 경로**이지 아카이브가 아니다.

### 판별 질문

값을 파일 이름·존재 여부·개수·타임스탬프로 알아내려 할 때 먼저 묻는다.

> **이 값을 갖고 있는 곳이 따로 있는가?**

있으면 거기서 읽는다. 파일시스템은 그 값을 **부수적으로** 반영할 뿐이라
반영 규칙이 바뀌면 조용히 어긋나고, 어긋나도 오류가 나지 않는다.

| 알고 싶은 것 | 간접 지표 (X) | 직접 출처 (O) |
| :-- | :-- | :-- |
| 실거래 자료 기준일 | 최신 날짜 폴더명 | `MAX(deal_date)` |
| 마지막 갱신 시각 | 마커 파일 mtime | `crawl_state["last_updated"]` |
| 적재 건수 | CSV 파일 크기 | `COUNT(*)` |

`자료 기준일`(마지막 거래가 언제인가)과 `갱신 시각`(언제 받아왔는가)은
서로 다른 값이므로 화면에 둘 다 남긴다. 하나로 합치면 이번과 같이
한쪽이 다른 쪽을 대신하다가 어긋난다.

셋 중 어느 것도 아니라면, 그 값은 애초에 입력으로 받아야 하는 것이다.
